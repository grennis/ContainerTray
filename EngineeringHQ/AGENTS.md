# Engineering HQ

A native macOS app that is the central place for engineering tooling and
status. It has a main window with a sidebar of modules and a menu bar icon
whose menu shows each module's quick actions. Closing the window keeps the
app running in the menu bar and hides the Dock icon until the window is
opened again.

It replaces two earlier apps:

- **Containers** module: from ContainerTray. Lists Apple `container` CLI
  containers and machines, starts/stops containers, opens a Terminal shell
  in a machine, starts/stops container services.
- **Monitor** module: from MonitorTray (Electron). Runs read-only `GET`
  checks against the public endpoints of the ChetBackend Vapor server in
  Local, Development and Production, validating each JSON body's shape.

## Project type

A real Xcode project generated by `xcodegen` from `project.yml`. Do not
hand-edit `EngineeringHQ.xcodeproj`. To change project settings, edit
`project.yml`, then run `xcodegen generate` in this directory.

## Architecture

```
EngineeringHQ/Sources/
  App/EngineeringHQApp.swift    Scenes: main Window + MenuBarExtra
  Core/HQModule.swift           The module protocol and ModuleHealth
  Core/ModuleRegistry.swift     The list of modules (register new ones here)
  Core/MainWindow.swift         Sidebar of modules + detail pane
  Core/MenuBarContent.swift     Menu bar menu and icon
  Core/StatusIcon.swift         Colored menu icons, sidebar health badge
  Modules/Containers/           Containers module
  Modules/Monitor/              Monitor module
```

Each feature is a self-contained module under `Modules/<Name>/`. A module is
a `@MainActor` `ObservableObject` conforming to `HQModule`. It provides an
`id`, `title`, SF Symbol, a `health` value, a detail view for the main
window and content for the menu bar menu. The shell never reaches into a
module's internals, and modules do not depend on each other.

### Adding a module

1. Create `EngineeringHQ/Sources/Modules/<Name>/`.
2. Add a `@MainActor final class <Name>Module: ObservableObject, HQModule`.
   Keep its state in `@Published` properties.
3. Return `AnyView(<Name>View(module: self))` from `makeDetailView()` and
   the menu items from `makeMenuContent()`. Those views hold the module as
   an `@ObservedObject`.
4. Add an instance to `ModuleRegistry.makeDefault()`.
5. Run `xcodegen generate` so the new files are in the project.

`health` drives the sidebar dot and the menu bar icon: `.failing` turns the
icon red, `.active` green (for example a running container). `.ok` and
`.idle` leave the icon monochrome.

## Key facts

- `MenuBarExtra` renders SF Symbol labels and menu item images as
  monochrome templates, ignoring `.foregroundColor`/`.renderingMode`. For a
  colored icon use `StatusIcon.colored(...)`, which builds a non-template
  `NSImage` with a palette color.
- `⌘R` in the main window is the selected module's primary action: Refresh
  for Containers, Run the selected environment for Monitor. Only the
  visible module's toolbar button is active, so they do not conflict.
- The app is not sandboxed: the Containers module shells out to the
  `container` CLI at `/usr/local/bin/container` or
  `/opt/homebrew/bin/container`, and uses `osascript` to open Terminal.
- Containers watches `~/Library/Application Support/com.apple.container`
  with FSEvents instead of polling. See `ContainerFSWatcher.swift`.
- `NSAllowsLocalNetworking` is set so Monitor can reach the Local
  environment over plain HTTP.

## Monitor rules

- Only add checks for endpoints that require no authentication and have no
  side effects. `GET` only. Do not add `POST` routes even if the backend
  accepts them anonymously.
- Every check needs a `validate` closure that asserts the body's shape, not
  just a 200 status. Checks live in `Modules/Monitor/EndpointCheck.swift`.
- Base URLs end in `/api/`. Relative paths resolve beneath it. Use a
  leading `/` for paths at the site root such as the health check.
- Backend routes are in `ensemble-swift/Packages/ChetBackend`,
  `Sources/App/routes.swift`.

## Build

The build machine may not have `xcode-select` pointed at a full Xcode
install. Set `DEVELOPER_DIR` explicitly and build with ad-hoc signing:

```bash
cd EngineeringHQ
xcodegen generate
export DEVELOPER_DIR=/Applications/Xcode-27.0.0-Beta.5.app/Contents/Developer
xcodebuild -project EngineeringHQ.xcodeproj -scheme EngineeringHQ \
  -configuration Debug -destination 'platform=macOS' build \
  CODE_SIGNING_ALLOWED=NO
```

Use `-configuration Release` for the build to install into `/Applications`.
CI builds the Debug configuration on every pull request that touches this
directory (`.github/workflows/engineering-hq.yml`).

## Installing / running

```bash
pkill -x EngineeringHQ 2>/dev/null
rm -rf /Applications/EngineeringHQ.app
cp -R "$(xcodebuild -project EngineeringHQ.xcodeproj -scheme EngineeringHQ \
  -configuration Release -showBuildSettings 2>/dev/null \
  | awk -F' = ' '/ BUILT_PRODUCTS_DIR /{print $2}')/EngineeringHQ.app" /Applications/
open /Applications/EngineeringHQ.app
```

Default to a Debug build-only verification (no install/relaunch) unless the
user asks to install or run the app.
